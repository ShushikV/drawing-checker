# Drawing Checker

Windows desktop-приложение для проверки инженерных PDF-чертежей.
На текущем этапе реализован просмотр первой страницы PDF: рендеринг PyMuPDF,
zoom колесом мыши (20–500%, с привязкой к курсору) и pan перетаскиванием
левой кнопкой. При zoom страница заново рендерится из PDF.
Закрытие viewer возвращает стартовое окно.

Реализованы маркеры замечаний и интерактивная правая панель: выбор,
переход к области, описание, текст требований и переключение статуса.
Подготовлена проверка формата записей общих допусков; её запуск требует
локальной нормативной базы с вручную подтверждёнными пунктами. ML/AI не реализованы.
Подготовлен нормативный слой: модели редакций документов, пунктов и правил,
строгая загрузка JSON, проверка связей и явная регистрация анализаторов.
Рабочая нормативная база пуста; подробности — в [standards/README.md](standards/README.md).
Добавлен CLI импорта локального PDF: исходный текст по страницам, консервативная
нормализация, кандидаты пунктов с трассировкой и processed JSON. Импорт не создаёт
машинных правил; все результаты требуют проверки человеком.

## Проверка demo-замечаний

1. Запустите приложение и включите флажок «Демо-замечания» на стартовом экране.
2. Откройте любой PDF. Справа появятся четыре вымышленных замечания;
   панель явно обозначена как ДЕМО. Без флажка запускается проверка общих допусков,
   если подготовлена нормативная база; иначе панель объясняет, почему проверка не выполнена.
3. Выберите первое замечание: область выделится синим и попадёт в видимую
   часть чертежа; ниже списка появятся описание и демонстрационное требование.
4. Выберите второе: обе области имеют номер 2 и подсвечиваются одновременно,
   переход выполняется к первой области. Проверьте zoom и pan.
5. Нажмите «Отметить как выполнено», затем «Вернуть ошибку».
   Статус меняется сразу; выполненные области пунктирные, неактивные — зелёные.
6. Выберите замечание ко всему документу и замечание на другой странице:
   ложных маркеров на первой странице нет, в деталях отображается пояснение.

Demo-области пропорциональны размеру первой страницы и не связаны с её содержимым.
Замечание на странице 2 демонстрационное, даже если в PDF всего одна страница.

## Локальный запуск (PowerShell)

Нужен Python 3.12+ с Tcl/Tk (компонент стандартного установщика Python для Windows).
Из корня репозитория:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m app.main
```

После установки также доступна команда `.\.venv\Scripts\drawing-checker.exe`.
Pillow и PyMuPDF устанавливаются как зависимости. Tkinter не устанавливается через pip.

## Тесты

```powershell
.\.venv\Scripts\python.exe -m pytest -p no:cacheprovider
```

Тесты viewer создают настоящие окна Tk, поэтому требуют доступного рабочего
стола. Используются небольшой временный PDF и исходный чертёж из fixtures.
Проверяются извлечение текста, разрешение и RGB-рендеринг, zoom/pan,
ограничения масштаба, закрытие окна и сбои открытия/рендеринга,
модель ошибки и выполнение тестовых правил. Дополнительно проверяются список,
выбор и статус замечаний, навигация к области, сохранение overlays при zoom,
несколько областей, отсутствие координат, другие страницы и преобразование
координат при поворотах 0/90/180/270°. Реальных правил ГОСТ в тестах нет.

## Архитектура

Связь данных и компонентов (стрелки показывают связи, а не порядок чтения файлов):

```text
PDF
 ↓
Document extraction
 ↓
RuleRunner / analyzers
 ↓
RuleDefinition
 ↓
Normative registry
 ↓
DrawingIssue
 ↓
Viewer
```

Перед запуском каталог загружается и валидируется. Приложение явно выбирает
активное правило, связывает его `check_type` с зарегистрированной реализацией
и передаёт адаптер в `RuleRunner`. Параметры поступают из `RuleDefinition`;
результат анализатора преобразуется в `DrawingIssue` со ссылками из каталога.
Документ-источник и машинное правило — разные сущности.

Будущий AI/RAG слой, **пока не реализован**:

```text
PDF/structure + relevant StandardClause
                    ↓
           AI-assisted analyzer
                    ↓
               DrawingIssue
```

- `app/main.py` — стартовое окно, выбор файла, запуск viewer и сообщения об ошибках открытия.
- `app/viewer.py` — `PdfViewer`, окно просмотра, Canvas, рендеринг и обработчики zoom/pan.
- `app/issue_panel.py` — список замечаний, подробности и кнопка статуса.
- `app/demo_issues.py` — отдельный источник вымышленных замечаний, без анализаторов.
- `app/pdf_reader.py` — доступ к PDF, геометрия страницы, текстовые фрагменты, растр и конвертация в Pillow.
- `app/models.py` — независимые от GUI модели `DrawingIssue`, `IssueLocation`,
  `BoundingBox`, `RequirementReference`, `Severity`, `IssueStatus`.
- `app/analysis/runner.py` — `AnalysisContext`, контракт `Rule` и `RuleRunner`.
  Правила передаются явно; реестр по умолчанию пуст. Ошибки выполнения
  передаются вызывающему коду, а не превращаются в успешный пустой результат.
- `app/standards/` — модели, строгий JSON-загрузчик и `NormativeRegistry`.
- `app/standards/importer.py`, `normalizer.py`, `clause_extractor.py` — отдельные
  этапы извлечения PDF, нормализации текста и выделения кандидатов пунктов.
- `app/standards/processed_writer.py`, `import_cli.py` — воспроизводимые JSON,
  provenance, защита перезаписи и CLI без GUI.
- `app/analysis/normative.py` — `AnalyzerRegistry`, `AnalyzerResult`, адаптер
  к существующему runner и преобразование в `DrawingIssue`.
- `standards/source/`, `standards/processed/`, `standards/rules/` — пустая
  структура нормативной базы. Синтетические данные есть только в тестах.

`DrawingIssue` имеет стабильный UUID, идентификатор правила, заголовок,
описание, серьёзность, статус, несколько мест на чертеже, ссылки на требования
и дополнительные метаданные. Статус можно переключить методами `mark_done()`
и `reopen()`. Сохранение результатов на диск пока не реализовано.

Индексы страниц начинаются с нуля. Области ошибок задаются в координатах
неповёрнутой страницы PDF, в пунктах (1/72 дюйма), начало — сверху слева.
Область без прямоугольника относится ко всей странице; ошибка без мест —
ко всему документу. Методы `pdf_point_to_canvas` и `pdf_bbox_to_canvas` учитывают
поворот страницы и масштаб viewer. Номера соответствуют порядку в переданном
списке, UUID от них не зависит.

`PdfViewer(master, file_path, issues=None, demo=False)` принимает список
`DrawingIssue` и сохраняет сами объекты: кнопка изменяет их статус через методы
модели. Выбор хранится по UUID. Canvas использует теги `pdf_image`, `overlay`,
`issue:<UUID>`, `issue_region`, `issue_number`, `active`. При рендеринге
изображение заменяется отдельно, overlays восстанавливаются из модели.
Границы прокрутки определяются изображением PDF, а не маркерами.

Для добавления правила достаточно реализовать `rule_id` и
`analyze(context)`, возвращающий последовательность `DrawingIssue`, затем
передать экземпляр в `RuleRunner`. Анализаторы не должны импортировать Tk.
Проверка общих допусков подключена через `general_tolerances/runtime.py`:
каталог → проверка verified-ревизий → привязка анализатора → RuleRunner → viewer.

## Ограничения

Показывается только первая страница. Для других страниц выводится сообщение,
переключения страниц нет. При нескольких областях переход выполняется к первой
на текущей странице; если область больше окна, показывается её начало.
Требования и URL представлены текстом, автоматического открытия ссылок нет.
Статусы живут в памяти текущего viewer и не сохраняются после закрытия.
Реальные документы и активированные производственные правила в поставку не входят;
OCR и AI отсутствуют. Базовое выделение пунктов не является универсальным парсером.
Проверка структуры не заменяет экспертизу
формализации человеком. История версий базы хранится в Git; автоматические
миграции и выбор применимой редакции пока не реализованы.

## Ручная верификация нормативных пунктов

Внутренний инструмент запускается отдельно от viewer чертежей:

```powershell
.\.venv\Scripts\python.exe -m app.standards.review_gui --standards-root standards
.\.venv\Scripts\python.exe -m app.standards.review_cli status example-standard
.\.venv\Scripts\python.exe -m app.standards.review_cli validate
```

`verification_service.py` управляет статусами и исправлениями, `verification_store.py`
сохраняет решения в `standards/verified/`, а `verification_source.py` проверяет
снимки импорта. Исходные processed-файлы не перезаписываются. История содержит
оператора, время, текст решения и ссылки на сохранённый исходный импорт.

Кандидат не считается подтверждённым автоматически. При изменении содержимого
импорта старые решения вычисляются как `stale`; простой новый timestamp не
делает их устаревшими. GUI работает и без локального PDF, показывая предупреждение.
Строгая проверка `NormativeRegistry.validate_rule_activation(...)` требует
актуальные verified-пункты и включается явно. Подробности workflow и ограничений —
в [standards/README.md](standards/README.md).

## Записи общих допусков (этап 6)

Поддерживаются следующие формы, в том числе внутри строки «Общие допуски по …»:

| Форма | Допустимые обозначения |
| --- | --- |
| `ГОСТ 30893.1 - m` | `f`, `m`, `c`, `v` |
| `ГОСТ 30893.1: H14, h14, ±t2/2` | также `±IT14/2` |
| `ГОСТ 30893.1: + t2, - t2, ±t2/2` | вариант приложения А.4 |
| `ГОСТ 30893.2-K` | `H`, `K`, `L` |
| `ГОСТ 30893.2-mK` | все 12 комбинаций `f/m/c/v` с `H/K/L` |

Пробелы проверяются отдельно от распознавания: вокруг разделителя 30893.1
они обязательны, в формах 30893.2 запрещены, включая промежуток между классами.
В приложении А пробел перед двоеточием запрещён, после двоеточия и запятых
обязателен. Между `+`/минусом и `t2` нужен пробел, между `±` и `t2` — нет.
Проверяется наличие пробела, а не его физическая ширина или единственность.

Разделители `-`, `–`, `—`, `−` эквивалентны по политике проекта. Дополнительно
учтён U+00AD: некоторые PDF-шрифты извлекают видимый дефис как мягкий перенос.
Он распознаётся как дефис и никогда не удаляется. Семантический минус сохраняется.
NBSP и узкий NBSP распознаются как пробелы; исходные `raw_text` и интервалы
символов остаются неизменными. Кириллические `Н`/`К` и `Н14` приводятся к ASCII
только в соответствующих технических обозначениях, без транслитерации текста.

`app/analysis/general_tolerances/` разделён на модель результата (`models.py`),
нормализацию (`normalization.py`), токенный parser (`parser.py`), проверку параметров
(`policy.py`), восстановление строк (`lines.py`), анализатор (`analyzer.py`)
и запуск (`runtime.py`). `config/general_tolerances.project.json` — проектный
профиль по постановке задачи, **не подтверждённый нормативный источник**.
При явной публикации его параметры копируются в `RuleDefinition.parameters`.

Parser возвращает `VALID`, `RECOGNIZED_INVALID` или `NOT_A_REFERENCE`.
Ошибочная, но распознанная запись даёт понятное объяснение: `invalid_spacing`,
`invalid_size_class`, `invalid_geometry_class`, `missing_class`,
`invalid_reference_format`, `incomplete_combined_reference`.
Замечание содержит найденный текст, ожидаемый формат, parsed-поля, diagnostics,
страницу, bbox и ссылку на конкретную verified-ревизию нормативного пункта.

Строки восстанавливаются из `extract_text_spans`: используются номера блока/строки,
направление текста и близость фрагментов. Текст объединяется без вставки или
схлопывания пробелов; карта символов указывает на исходные spans. Bbox записи —
объединение покрывающих её spans. Если запись занимает часть одного span,
выделение может захватывать соседний текст. Визуальный зазор без текстового
пробела отмечается как `uncertain_pdf_spacing`: нужен просмотр пользователем.

Поиск идёт по всему текстовому слою всех страниц; область ТТ пока не определяется.
Предусмотрен будущий фильтр областей. Перенос одной записи между строками не
поддерживается. Отсутствие ссылки не считается ошибкой. Численные значения
допусков, применимость класса и обязательность ссылки не интерпретируются.
Скан без текстового слоя требует будущего OCR. Анализ выполняется синхронно;
viewer по-прежнему показывает только первую страницу.

Для ручной проверки сначала подготовьте базу по инструкции
[standards/README.md](standards/README.md#подготовка-правил-общих-допусков).
Запустите `python -m app.main`, оставьте «Демо-замечания» выключенным и откройте
PDF с текстовыми строками `ГОСТ 30893.2-mK`, `ГОСТ 30893.2 - mK` и
`ГОСТ 30893.1 - x`. Первая запись не должна давать замечание; следующие две
должны дать замечания о пробелах и классе. Выберите замечание, проверьте маркер,
нормативный текст, zoom/pan и переключение статуса выполнения.
Без базы приложение показывает «проверка не выполнена», а не успешный результат.
