# Нормативный слой Drawing Checker

## Подготовка правил общих допусков

В поставке нет исходных ГОСТ, подтверждённых пунктов или производственных
RuleDefinition. Не используйте синтетические тестовые подтверждения в рабочей базе.

1. Положите локальные документы `ГОСТ 30893.1-2002.pdf` и
   `ГОСТ 30893.2-2002.pdf` в `standards/source/`. PDF не добавляются в Git.
2. Из корня проекта выполните команды ниже, используя Python из `.venv`.

```powershell
python -m app.standards.general_tolerance_rules import-sources
python -m app.standards.review_gui --standards-root standards
```

Импорт использует существующий workflow и расширенное распознавание кандидатов
приложения А. Он не подтверждает текст и не активирует документ. В инструменте
review вручную сверьте с PDF текст, номер и границы раздела 6 и пункта А.4
ГОСТ 30893.1, пунктов 7.1 и 7.2 ГОСТ 30893.2. Исправьте ошибки извлечения и
явно подтвердите пункты. Если нужные границы не извлечены, сначала исправьте
импорт; не подтверждайте другой пункт вместо нужного.

После экспертизы документа администратор должен явно изменить только его
административное поле `status` в processed-карточке документа на `active`.
Импорт создаёт `draft`; GUI подтверждения пунктов статус документа не меняет.
Административный статус исключён из fingerprint и не заменяет проверку пунктов.
Также сверьте `config/general_tolerances.project.json` с подтверждёнными
требованиями: это проектная формализация, а не извлечённые нормативные данные.

```powershell
python -m app.standards.general_tolerance_rules status
python -m app.standards.general_tolerance_rules publish-rules
```

Публикация разрешена только после `validate_rule_activation(...)` для всех
четырёх пунктов. Создаются четыре определения в `rules/general_tolerances/`:
`eskd.general_tolerances.size` (6), `.appendix` (А.4), `.geometry` (7.1),
`.combined` (7.2). Параметры классов, форм, пробелов и тире записываются в
каждое определение. Повторная автоматическая перезапись запрещена.

Правила фиксируют revision и import fingerprint подтверждения. Привязка
анализатора требует VerificationService; проверка активности и актуальности
выполняется перед анализом и после него. Candidate/rejected/stale, изменённая
ревизия или импорт блокируют запуск: нельзя продолжать со старым нормативным
объяснением. После изменения подтверждения требуется сознательный пересмотр
правил и их закреплённых ревизий. В описания замечаний попадают исправленный
текст и номер verified-пункта, сведения об операторе и источнике.

При отсутствии базы viewer работает, но сообщает, что проверка не выполнена.
Команда `status` в этом состоянии возвращает код 1. Все варианты формы и
ограничения анализа описаны в корневом README.

Это инфраструктура версионируемой базы ЕСКД. Каталог пока пуст: здесь нет
реальных текстов ГОСТ, нормативных значений или исполняемых проверок ЕСКД.
Все синтетические данные расположены отдельно в `tests/fixtures/normative/`
и явно помечены `TEST FIXTURE ONLY`. Их нельзя переносить в рабочую базу.

## Структура

```text
standards/
  source/                 Исходные документы, доступные на законных основаниях
  processed/
    documents/            JSON-карточки конкретных редакций документов
    clauses/              JSON-карточки пунктов, включая непроверенные кандидаты
    imported/             Исходный/нормализованный текст страниц и diagnostics
    imports/              Отдельные записи импорта с timestamp
  rules/                  JSON-определения машинных правил
```

`source` хранит первоисточники. `processed` хранит нормализованные данные и
связи с ними. `rules` хранит интерпретацию, подготовленную для алгоритма.
Загрузчик каталога читает только JSON-карточки документов, пунктов и правил.
Отдельный importer извлекает текст PDF и создаёт черновые карточки без правил.
Реальные нормативные документы могут иметь ограничения по лицензированию и
распространению. Перед размещением первоисточника или выдержек необходимо
проверить права; наличие файла на диске само по себе не разрешает его публикацию.

## Нормативный документ != машинное правило

`StandardDocument` описывает конкретную редакцию документа, `StandardClause` —
связанный с ней пункт с исходным текстом. `RuleDefinition` задаёт, какую
проверку запустить и с какими параметрами. Формализация не заменяет источник:
одно правило может ссылаться на несколько пунктов одного документа, а один
пункт может поддерживать несколько правил.

Python-анализатор знает **как проверять**. Нормативные значения хранятся в
`RuleDefinition.parameters`; их нельзя зашивать в Python-код анализатора.
`check_type` — ключ зарегистрированной реализации, а не имя Python-модуля
для динамического импорта. Загрузка файла никогда не исполняет код.

## Модели и формат

Используется JSON UTF-8: стандартная библиотека Python, отсутствие новых
зависимостей, явные строки/числа/массивы и строгая проверка структуры. В отличие
от YAML, JSON не поддерживает комментарии; пояснения следует хранить в
`description` и `metadata`. Один файл содержит одну сущность, без внешней оболочки.

| Сущность | Обязательные поля | Необязательные поля |
| --- | --- | --- |
| StandardDocument | id, title, designation, version, source_path, status | effective_date, metadata, provenance |
| StandardClause | id, document_id, clause_number, source_text | title, page, metadata, normalized_text, page_end, source_spans |
| RuleDefinition | id, title, description, category, standard_document_id, clause_ids, check_type, parameters, automation_level, status, severity, version | metadata |

`version` документа — непустая строка редакции; `version` правила — целое число
от 1. Вместо отдельных `edition` и `version` у документа одно поле `version`,
чтобы не хранить два противоречащих друг другу обозначения редакции.
`effective_date` — `YYYY-MM-DD` или `null` (в Python — `date | None`).
Неизвестную дату не нужно придумывать. Наличие даты не меняет статус автоматически.

`clause_ids` в JSON — массив уникальных идентификаторов пунктов, в модели —
кортеж. Это **id карточек**, а не номера пунктов: отображаемый номер хранится
в `clause_number`. Пустой массив допустим для ссылки на документ в целом.
`page` — номер страницы первоисточника, начиная с 1; он не связан с нулевым
индексом страницы проверяемого чертежа в `IssueLocation`.

`parameters` и `metadata` — JSON-объекты со строковыми ключами и конечными
JSON-значениями. `category` и `check_type` — непустые строки; их набор расширяемый.
Допустимые значения перечислений:

- StandardStatus: `draft`, `active`, `superseded`, `archived`.
- RuleStatus: `draft`, `verified`, `active`, `deprecated`.
- AutomationLevel: `deterministic`, `ai_assisted`, `manual`.
- Severity: `info`, `warning`, `error`.

Модели не импортируют GUI. В прямом Python-конструкторе передавайте enum,
`date` и кортеж; загрузчик преобразует соответствующие JSON-значения явно.

## Версии и жизненный цикл

Жизненный цикл правила: **draft → verified → active → deprecated**.

- `draft` — формализация ещё не проверена.
- `verified` — формализация проверена человеком, но ещё не включена в работу.
- `active` — явно разрешена к использованию.
- `deprecated` — выведена из применения, сохраняется для истории.

Автоматически сгенерированное правило нельзя считать нормативно достоверным
до проверки человеком: необходимо проверить источник, редакцию, смысл,
область применимости и параметры. В `metadata` можно записывать сведения
о проверившем, дате и основании решения. Загрузчик проверяет структуру и связи,
но не доказывает, что человек провёл экспертизу, и не ведёт журнал переходов.
Присвоение строки `active` само по себе не является нормативной экспертизой.

`StandardDocument.id` должен идентифицировать конкретную редакцию. При новой
редакции создавайте новую карточку с новым id, затем связанные пункты и новую
версию правил. `StandardClause.id` уникален во всём каталоге и также должен
учитывать редакцию документа. Номер пункта сам по себе не является глобальным id.

В одном снимке каталога допустима одна версия каждого rule id; старые версии
хранятся в истории Git или отдельном снимке базы. Повышайте `RuleDefinition.version`
при изменении параметров или интерпретации. Автоматического выбора «последней»
редакции, миграций формата и загрузки нескольких версий одного rule id пока нет.

## Добавление данных

1. Подготовьте разрешённый первоисточник в `source/` или согласованном локальном
   хранилище. Не добавляйте его в Git без прав на распространение.
2. Импортируйте PDF через CLI ниже либо создайте JSON в `processed/documents/` со всеми обязательными полями
   `StandardDocument`. Начните со статуса `draft`. `source_path` — непустая
   ссылка-путь к исходному файлу, для ручных карточек — относительно `standards/`.
   Импортер сохраняет только имя файла и `metadata.source_path_kind=filename_only`,
   поскольку файл может поступить из произвольного локального хранилища.
   Загрузчик хранит путь как данные: не открывает его и не проверяет существование.
3. Создайте JSON в `processed/clauses/`: уникальный id, существующий `document_id`,
   точный номер, проверенный `source_text`, при наличии страницу и заголовок.
4. Создайте JSON в `rules/` со всеми полями `RuleDefinition`, статусом `draft`,
   ссылками на документ и пункты, параметрами и ключом `check_type`.
   Структуру файлов можно изучить в явно синтетических тестовых fixtures;
   они не являются нормативными образцами.
5. Загрузите весь каталог, проверьте ошибки и проведите содержательную проверку
   человеком. Только затем переводите правила в `verified` и `active`.

```python
from app.standards import NormativeRegistry, RuleStatus

catalog = NormativeRegistry.from_directory("standards")
active = catalog.active_rules()
drafts = catalog.find_rules(status=RuleStatus.DRAFT)
text_rules = catalog.find_rules(category="text", status="active")
# catalog.get_rule(rule_id), get_document(document_id), get_clause(clause_id)
```

`from_directory` читает JSON рекурсивно в отсортированном порядке, без `source/`.
Для произвольных путей есть `from_files(document_files=..., clause_files=...,
rule_files=...)`. Каталог публикуется только после успешной проверки всех данных.
Он является снимком: для обновления загрузите новый экземпляр. Полученные из
него модели — копии, поэтому изменение вложенных параметров не меняет каталог.

## Валидация

Загрузчики `load_document`, `load_clause`, `load_rule` проверяют отдельный файл:
обязательные и неизвестные поля, непустые строки, enum, типы, дату, версию,
страницу, параметры и метаданные. Нет неявного приведения `"1"` или `true`
к целочисленной версии. Повторные JSON-ключи и `NaN`/бесконечности отвергаются.
Ошибки файла включают путь и поле; используется `NormativeValidationError`.

`NormativeRegistry` дополнительно проверяет:

- уникальность id документов, пунктов и правил;
- наличие документа каждого пункта и правила;
- наличие указанных пунктов, если каталог пунктов загружен;
- принадлежность каждого пункта именно документу данного правила;
- активное правило может ссылаться только на активный документ.

`clauses=None` означает, что каталог пунктов не загружен; `clauses=[]` — загружен
и пуст. В первом случае проверка ссылок на пункты отложена, во втором неизвестные
пункты запрещены. При загрузке каталога из папки существование
`processed/clauses/` означает, что каталог пунктов загружен.
Для исполнения правила с пунктами полная загрузка пунктов обязательна.
Неизвестные id при поиске дают `NormativeLookupError`.

## Связь с анализаторами

Контракт расположен в `app/analysis/normative.py`. Реализация предоставляет:

```python
def validate_parameters(self, parameters: dict[str, object]) -> None:
    # Проверка схемы параметров данного check_type; ValueError при ошибке.
    ...

def analyze(self, context, *, parameters: dict[str, object]):
    # Возвращает последовательность AnalyzerResult, по одному на замечание.
    ...
```

Регистрация и выбор правила выполняются явно кодом приложения:

```python
from app.analysis import RuleRunner
from app.analysis.normative import AnalyzerRegistry

implementations = AnalyzerRegistry()
# analyzer — уже созданная и протестированная реализация, не текст из JSON.
# implementations.register("your_check_type", analyzer)
# bound_rule = implementations.bind(rule_id, catalog)
# issues = RuleRunner([bound_rule]).analyze(context)
```

`bind` находит правило, проверяет его статус и уровень автоматизации, наличие
пунктов и зарегистрированной реализации, затем валидирует параметры.
Поддерживается исполнение только `active` + `deterministic`; `ai_assisted`
и `manual` пока лишь значения модели. Неизвестный `check_type` допустим в
каталоге данных, но при попытке исполнения возникает `AnalyzerNotFoundError`.
Повторная регистрация ключа запрещена. `RuleRunner` не изменён и не запускает
все правила каталога автоматически; в GUI каталог пока не подключён.

Анализатор получает копию `parameters` на каждый запуск. Он возвращает
`AnalyzerResult` с координатами, необязательным наблюдением и метаданными.
Преобразователь `issue_from_result` переносит в `DrawingIssue`:

- id, заголовок, описание и severity правила; наблюдение дописывается к описанию;
- все координаты результата;
- обозначение и редакцию документа, id и номер пункта, исходную выдержку и страницу;
- раздельные metadata: `normative` (версия правила, источник, параметры),
  `rule_metadata` и `analysis`, без взаимного перезаписывания.

`RequirementReference` расширен необязательными полями; прежние позиционные
аргументы `document`, `section`, `url` сохраняют смысл. Viewer получает только
`DrawingIssue` и показывает доступные сведения ссылки, не импортируя каталог.

В рабочем коде нет ни одного анализатора ЕСКД. Mock-анализатор находится только
в `tests/test_normative_analysis.py`. Будущий AI/RAG слой может использовать
проверенные `StandardClause` как контекст. Извлечение текста PDF и базовых
кандидатов пунктов реализовано; поиск, интерпретация и AI не реализованы.

## Импорт нормативного PDF (этап 4)

Исходный файл разместите локально в `standards/source/`. `.gitignore` исключает
все исходники и вложенные папки; отслеживаются только `.gitkeep` и README.
Это правило не распространяется на `tests/fixtures/`. Processed-текст по умолчанию
не игнорируется, чтобы его можно было проверять в code review, но право на его
распространение необходимо проверить отдельно. Не публикуйте его автоматически.

Пример PowerShell из корня репозитория (имя и реквизиты условные, не реальный ГОСТ):

```powershell
.\.venv\Scripts\python.exe -m app.standards.import_cli `
  standards/source/example.pdf `
  --id example-standard `
  --designation "TEST" `
  --title "Test standard" `
  --version "1"
```

Если нужное окружение уже активно, можно использовать `python -m ...`.
`--standards-root <папка>` меняет корень выходной базы, по умолчанию это
`standards` относительно текущей рабочей папки. Исходный PDF можно передать
из другой папки: абсолютный путь используется только во время работы и в JSON
не записывается. Название, обозначение, редакция и id задаются пользователем;
импортер не пытается угадать их из титульного листа.

CLI показывает количество страниц, число кандидатов пунктов, SHA-256,
diagnostics/warnings и каждый созданный путь. Код возврата 0 означает успешный
импорт, 1 — ошибку чтения/валидации/записи, 2 — неверные аргументы CLI.
Предупреждения не считаются ошибкой импорта и требуют проверки человеком.
GUI для импорта не добавлен.

### Архитектура

```text
PDF (исходные байты)
  ↓ StandardPdfImporter: чтение, SHA-256, PyMuPDF, без записи исходника
ImportedPage[] (source_text отдельно по страницам)
  ↓ TextNormalizer
NormalizedPage[] (source_text + normalized_text + позиции строк)
  ↓ ClauseExtractor / NumberedClauseExtractor
StandardDocument(draft) + StandardClause[] + diagnostics
  ↓ processed_writer: валидация, staging, сериализация
processed JSON
  ↓ существующие строгие loader / NormativeRegistry
```

`app/standards/import_types.py` содержит промежуточные представления и
типизированные ошибки. `importer.py` координирует извлечение, `normalizer.py`
обрабатывает переводы строк, `clause_extractor.py` выделяет кандидаты,
`processed_writer.py` отвечает за файлы, `import_cli.py` — за аргументы и вывод.
Регистрация и исполнение правил остаются отдельной подсистемой.

### Происхождение и воспроизводимость

`StandardDocument.provenance` содержит:

- `source_filename`, `sha256`, `file_size` в байтах, `page_count`;
- `importer_version`, `extraction_engine` с версией PyMuPDF;
- `normalizer_version`, `clause_extractor_version`;
- `import_record` — относительный путь к отдельной записи импорта.

SHA-256 вычисляется по **исходным байтам PDF**, а не по извлечённому тексту.
PyMuPDF получает тот же снимок байтов в памяти: файл между подсчётом хеша
и извлечением не перечитывается. Исходный файл не изменяется.

Для одинаковых байтов, имени файла, введённых реквизитов и версий всех этапов
(включая PyMuPDF) основные JSON-файлы побайтово одинаковы. JSON записывается
в UTF-8 без BOM, с сортировкой ключей, отступом 2 и переводами строк LF.
Абсолютные рабочие пути и случайные UUID в эти данные не добавляются.
Произвольный текст самого PDF при этом не цензурируется.

Timestamp UTC вынесен в `processed/imports/<id>.json` вместе с id, SHA-256
и версией импортера. Это запись **последнего импорта**, а не журнал событий.
`provenance.import_record` позволяет найти её из карточки документа.
В основном документе, страницах и пунктах timestamp отсутствует, поэтому
повторный импорт меняет только запись события. Разные версии движка извлечения
могут давать различия текста; используйте одинаковое окружение для воспроизведения.

### Формат processed и трассируемость

```text
processed/
  documents/<id>.json          Один StandardDocument
  clauses/<id>/0001.json       Один StandardClause на файл
  clauses/<id>/0002.json
  imported/<id>.json           Страницы, позиции строк и diagnostics
  imports/<id>.json            Timestamp UTC и привязка к SHA-256
```

Раздельные файлы пунктов сохраняют существующий контракт «одна сущность — один
JSON». Каталог рекурсивно читает документы и пункты; служебные `imported/` и
`imports/` не выдаются за нормативные сущности. Перед публикацией writer повторно
загружает staged-карточки существующими строгими загрузчиками и проверяет полный
каталог, включая уже имеющиеся правила. Невалидный каталог не перезаписывается.

У импортированного пункта сохраняются `document_id`, `clause_number`,
`source_text`, `normalized_text`, `page`, `page_end` и `source_spans`.
Номера страниц начинаются с 1. Каждый span хранит страницу и полуоткрытые
интервалы `[source_start, source_end)` / `[normalized_start, normalized_end)`.
Это смещения **символов Python Unicode в извлечённом тексте страницы**, не
байтовые позиции PDF и не координаты на листе. Проверяются границы, порядок,
длины и точное совпадение с текстом соответствующих страниц перед записью.
Текст многополосного пункта собирается из фрагментов страниц через дополнительный
`\n`; сами фрагменты сохраняются неизменными и восстанавливаются по spans.

`title` у базового extractor остаётся `null`: первая строка с номером может быть
как заголовком, так и началом требования, поэтому это не угадывается. Она целиком
сохраняется в тексте пункта. `metadata.review_required=true` помечает кандидата.
Старые карточки без новых полей по-прежнему загружаются.

### Нормализация и выделение пунктов

Нормализатор заменяет CRLF/CR на LF и удаляет только BOM в начале страницы.
Он не меняет орфографию, пробелы, Unicode-символы, переносы слов и смысл текста.
Исходная строка страницы хранится рядом. NUL и символ замены сохраняются с
diagnostic о возможной проблеме кодировки.

Базовый extractor распознаёт строки «номер + пробел + текст» с номерами
`1`, `1.1`, `1.1.1`, `5.2.3`. Каждая такая граница помечается как кандидат для
ручной проверки. Ненумерованные последующие строки продолжают текущий пункт.
Продолжение на следующей странице поддерживается, но сопровождается отдельным
warning: в него могли попасть колонтитулы.

Голый номер, повторный номер, строки с точками-лидерами и явно числовые табличные
строки не угадываются: текущий пункт закрывается, фрагмент остаётся только в
тексте страницы с warning. Нераспознанный текст до первого пункта тоже сохраняется
с diagnostic. Пустая страница прерывает продолжение и получает предупреждение.
Непустой PDF без выделенных пунктов может быть импортирован с нулём кандидатов:
весь его текст остаётся в `imported/<id>.json`.

Новый extractor реализует `version` и `extract(document_id, pages)` и возвращает
`ClauseExtraction`. Он передаётся в `StandardPdfImporter(clause_extractor=...)`.
Параметры формализации правил к этому контракту не относятся.

### Повторный импорт и защита записи

- При существующих данных того же id и том же SHA-256 требуется `--overwrite`.
- При другом или неизвестном предыдущем SHA-256 возникает `SourceHashConflict`.
  Предпочтительно использовать новый id редакции; для намеренной замены нужны
  оба флага `--overwrite --accept-source-change`, а CLI дополнительно выводит warning.
- Перезапись заменяет весь управляемый набор пунктов данного документа, удаляя
  устаревшие кандидаты. Ручные изменения этих файлов также будут заменены.
  Исходный PDF, другие документы и определения правил не перезаписываются.
- На время записи используется `.import.lock`. Данные готовятся и проверяются
  во временной папке, затем заменяются; обычная ошибка записи вызывает откат.
- Если откат тоже не удался, backup и lock сохраняются. Восстановление требует
  ручной проверки. При аварийном завершении сначала убедитесь, что импорт не
  выполняется, и проверьте временные данные, прежде чем удалять оставшийся lock.
  Это не транзакционная БД с гарантией восстановления после отключения питания.

Идентификатор ограничен переносимым именем файла: латинские буквы, цифры,
`_`, `-`, `.`, до 100 символов, без конечной точки и зарезервированных имён Windows.
Пути через symlink/junction для выходных файлов отвергаются. Writer также
запрещает выходной набор, который мог бы заменить сам исходный PDF.

### Ограничения и проверка человеком

OCR не реализован. PDF без извлекаемого текстового слоя даёт типизированную
ошибку `DocumentRequiresOCR` с сообщением `document requires OCR`. Частично
сканированный PDF импортируется с предупреждениями о страницах без текста;
импорт не доказывает полноту извлечения. Зашифрованные PDF с паролем не поддержаны.

Нет универсального parser ГОСТ: таблицы, колонки, оглавления, списки и
колонтитулы могут требовать другого extractor и ручного исправления. PyMuPDF
возвращает текст в порядке PDF, который не всегда совпадает с порядком чтения.
Файл и извлечённый текст обрабатываются в памяти; лимиты размера и фоновая
обработка пока не предусмотрены.

**Processed != проверенное машинное правило.** Импорт создаёт только документ
`draft` и кандидаты пунктов. Автоматическое выделение требует проверки человеком.
Импорт не означает юридическую или нормативную достоверность данных и не
порождает `RuleDefinition`. Реальные нормы, OCR, LLM и AI не применяются.

## Ручная верификация пунктов (этап 5)

**Candidate != verified.** Автоматически выделенный пункт остаётся кандидатом,
пока оператор явно не подтвердит текст и границы. Исходные `processed`-данные
инструмент проверки не редактирует: они нужны для сравнения с решением человека.

```text
import pipeline → immutable imported data
                           ↓
                 VerificationService
                           ↓
                  verified revisions
                           ↓
                 NormativeRegistry
                           ↓
                    RuleDefinition
```

`verification_models.py` содержит статусы, source reference и
`VerifiedClauseRevision`; `verification_source.py` проверяет снимки импорта;
`verification_store.py` хранит историю; `verification_service.py` реализует
переходы, сохранение, фильтры и проверку актуальности. GUI и CLI — клиенты сервиса.
Модель `StandardClause` остаётся исходным результатом extractor.

### Запуск внутреннего GUI

Из корня репозитория в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m app.standards.review_gui --standards-root standards
```

Сначала импортируйте локальный PDF через `import_cli`. Слева выберите документ,
пункт и фильтр статуса. В центре показана страница исходного PDF, доступны
переходы к началу/концу диапазона, перелистывание, масштаб и перемещение мышью.
Точных bbox у импортированных пунктов пока нет, поэтому ложной подсветки нет.

Справа доступны номер, заголовок, диапазон страниц, вкладки raw/normalized,
редактируемый текст решения, diagnostics/provenance, примечание и имя оператора.
Имя — обычная строка; системы пользователей нет. Кнопка истории показывает
предыдущие решения вместе с исходными кандидатами тех импортов.

- «Подтвердить» сохраняет введённые поля как `verified` с `verified_by` и `verified_at`.
- «Сохранить исправления» сохраняет текст, но устанавливает `needs_review`.
- «Нужно проверить» снимает актуальное подтверждение и ставит `needs_review`.
- «Отклонить» сохраняет `rejected`.

Для каждого решения сохраняются оператор `reviewed_by`, время `saved_at`,
примечание и метаданные. Поля `verified_by`/`verified_at` заполнены только у
подтверждённой ревизии. Предыдущее подтверждение остаётся в истории, но не
используется вместо более нового решения `needs_review` или `rejected`.

Первоначальный `candidate` — отсутствие сохранённого решения. Кандидат может
стать `needs_review`, `verified` или `rejected`. Отклонённый пункт сначала нужно
вернуть в `needs_review`, затем подтвердить. Возврат истории в `candidate`
запрещён. Правка подтверждённого пункта без нового подтверждения снимает его
пригодность для строгой активации правил.

Чтение и переключение фильтров не создают ревизий. Сохранение изменённого
решения увеличивает номер ревизии; повторное идентичное подтверждение тем же
оператором не создаёт дубликат. GUI передаёт ожидаемые номер ревизии и fingerprint
импорта: если данные изменились после открытия формы, сохранение отклоняется.

### Исходный PDF и сохранность данных

GUI ищет `source_filename` внутри `standards/source/`, включая вложенные папки.
Перед показом проверяется SHA-256; файл с тем же именем, но другими байтами,
не показывается как исходник. При отсутствии файла выводится
«Исходный PDF недоступен локально», при этом текст, metadata и решения доступны.
Подтверждение без локального PDF возможно по явному действию оператора,
например после сверки с внешним экземпляром; оно не означает автоматическую
проверку первоисточника программой.

Результаты находятся в `standards/verified/`, отдельно от импортера. Снимки в
`verified/sources/` сохраняют первоначальные raw/normalized, spans, страницы,
SHA-256, сведения об импортере и запись импорта даже после переимпорта PDF.
Исправленные поля находятся только в ревизиях. Их новый диапазон страниц не
выдаётся за автоматически извлечённые точные координаты текста.
Подробная структура описана в [verified/README.md](verified/README.md).

### Устаревшие решения — stale

`stale` вычисляется при чтении, а не записывается вместо решения человека.
Fingerprint включает воспроизводимое содержимое карточки документа,
provenance/версии инструментов, кандидаты всех пунктов и страницы с diagnostics.
Timestamp импорта исключён; административный статус документа также исключён.

Изменение PDF, версии импортера, текста, границ или состава пунктов меняет
fingerprint. Сохранённое решение становится `stale` и требует повторной проверки.
Это консервативная проверка на уровне документа: изменение одного пункта может
сделать устаревшими решения по другим пунктам того же импорта. Идентичный
переимпорт, изменивший только timestamp, не создаёт false stale.

История не удаляется. Исчезнувший из нового импорта пункт с сохранённым решением
остаётся видимым как `stale`; подтвердить отсутствующего кандидата нельзя.
Нужно восстановить/исправить импорт. Старые решения по удалённому документу также
обнаруживаются проверкой storage.

### CLI состояния и целостности

```powershell
.\.venv\Scripts\python.exe -m app.standards.review_cli status example-standard --standards-root standards
.\.venv\Scripts\python.exe -m app.standards.review_cli validate --standards-root standards
```

`status` показывает total, candidate, needs_review, verified, rejected и stale.
В total включаются исторические пункты, исчезнувшие из текущего импорта, если
у них есть решения. `validate` возвращает 1 при повреждённой структуре JSON,
некорректных ссылках/fingerprint, разрыве нумерации ревизий или любом stale-решении;
0 — когда целостность соблюдена и stale нет. Наличие кандидатов не является
ошибкой целостности и не означает их подтверждения.

Для согласованного чтения/записи используется тот же временный `.import.lock`,
что и у importer. При занятом или оставшемся после аварии lock операция не
продолжается автоматически. Проверять и убирать аварийный lock следует только
после проверки, что импорт/сохранение не выполняется.

### Будущая активация правил

Добавлена явная проверка:

```python
revisions = catalog.validate_rule_activation(rule_id, verification_service)
```

Она требует активный документ, явные ссылки на пункты, актуальный снимок каталога
и последнее решение `verified`, которое не является stale. Метод возвращает
проверенные ревизии и не меняет статус правила. Обычная загрузка каталога и
существующие тестовые правила сохраняют прежнее поведение; автоматического
включения этого режима в RuleRunner нет.

Целевой принцип: **active rule → verified non-stale clause**. Отредактированный
номер/текст берётся из возвращённой ревизии, а стабильный clause id связывает её
с исходным пунктом. Реальные правила, OCR и AI по-прежнему не создаются.

### Ограничения инструмента

Нет авторизации, цифровых подписей, merge/split пунктов или редактирования bbox.
Операции выполняются синхронно; большие базы и PDF могут замедлять интерфейс.
Не закрывайте окно с несохранёнными изменениями: они живут только в форме.
Проверка структуры и хешей не заменяет экспертизу содержания человеком.
